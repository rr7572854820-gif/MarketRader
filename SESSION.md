# MarketRadar — Session Journal

This is the project's running development journal. It is not a status dashboard and not a changelog — it is a record of what actually happened in each working session, including the reasoning, the mistakes, and the open threads, so that the next session (human or Claude) can pick up with full context instead of re-deriving it.

**Update this file at the end of every development session.** A session that isn't logged here didn't happen, as far as future sessions are concerned. See [CLAUDE.md](./CLAUDE.md) §13 for documentation standards this file should follow.

Do not delete old entries. This file is additive — append new sessions above or below consistently (this project logs newest-first) rather than overwriting history. If the file grows unwieldy, that's a future problem to solve deliberately (e.g., archiving old entries to a dated file), not a reason to delete the record silently.

## Session — 2026-08-06 (Thread num_reports through the dashboard's "all" run, and two blocking discoveries along the way)

### Current Objective
Make `source="all"` dashboard runs send `num_reports` (so `Pipeline.run()`'s oversample/split-across-sources logic actually engages), stated as a small, single-file dashboard edit ("add `num_reports: limit` to the payload object").

### Completed Work
- Read the two named files first, per the task's own instruction, and found the literal file path was wrong (`dashboard/src/lib/client.ts` doesn't exist - the real path is `dashboard/src/lib/api/client.ts`), consistent with every prior task's given paths needing correction.
- **Found and flagged, before writing anything, that the literal single-file edit could not achieve its own stated verification goal at all**: `source="all"` (and `"github"`/`"hackernews"`) always uses the SSE streaming path (`hasNoMockEquivalent(source)` is `true` for all three), which builds its own separate params object directly in `analysis-progress.tsx` - never touching `buildPayload()`, the function this task named. Worse, `client.ts`'s `AnalyzeStreamParams` had no `num_reports` field, and the backend's `GET /analyze/stream` route (`src/api/routes.py`) didn't accept one as a query parameter at all - even a frontend fix alone would have been silently ignored. Confirmed via `AskUserQuestion`: authorized to extend into `analysis-progress.tsx`, `routes.py` (backend), and `types.ts` (a fourth, mechanically-necessary companion type file, added without a separate pause since it was a trivial, non-judgment-call addition) to make the fix real rather than cosmetic.
- **A second, independent, more severe problem surfaced only through live end-to-end testing** (not something inspection alone would have caught): `src/api/app.py` never configured logging at all (no `basicConfig`) - so every `logger.info()` call anywhere in the app, run via `uvicorn src.api.app:app` (Render's presumed start command), was silently invisible; only WARNING+ fell through to Python's default last-resort handler. This affected far more than this task's diagnostic lines - the entire app's existing INFO-level operational logging (fetch/extract/cluster progress, the `[DIAGNOSTIC]` lines from an earlier task) has likely never been visible in Render's logs at all. Confirmed via `AskUserQuestion` before fixing: added the same `logging.basicConfig(WARNING) + logging.getLogger("src").setLevel(INFO)` pattern `src/pipeline/runner.py`'s own `_configure_logging()` already uses for the CLI - same reasoning (keep third-party libraries quiet, surface only this project's own logs), just applied to the API entrypoint, which had never had it.
- **A third, independent, structural problem was found only by then actually re-running the live-verified request end-to-end**: `num_reports: limit` (the literal fix, using the same numeric value for both) makes `PipelineConfig.post_limit == num_reports` always. `_initial_fetch_limit()` computes `min(calculate_fetch_limit(num_reports), post_limit)` - since `calculate_fetch_limit()` always returns *more* than its input (1.1x-3x multiplier), and `post_limit` equals `num_reports` under this exact wiring, the `min()` always just returns `post_limit` unchanged. Oversampling can never take effect, for any input value, under `num_reports: limit`'s literal design - not an edge case, a guaranteed self-collision. Live-confirmed against a real local server before reporting it: `limit=10, num_reports=10` still produced `Fetch limit per source: 5`, not 15. ### Architecture Review
1. **Module boundaries**: No violation — `GitHubFetcher` depends only on `src.config.Config`, `src.fetchers.base`, `src.models`, and its own new `exceptions.py`; nothing in `src/pipeline/`, `src/insights/`, etc. was touched or needs to know GitHub exists.
2. **Fetching comments inside the fetcher — single responsibility?** Consistent with `RedditFetcher`, which already fetches a submission's comments inside the same `fetch()` call. Not a new pattern.
3. **Hidden assumptions about GitHub's response shape**: several, all defended with `.get(...)` fallbacks rather than direct indexing — a missing `user`, `reactions`, or `body` degrades to a sane default (`"[unknown]"`, `0`, `""`) instead of raising `KeyError`. 4. **What breaks if GitHub changes its response format?** A renamed/removed field silently degrades (empty string / `"[unknown]"` / score `0`) rather than crashing, by the same `.get()` discipline above — consistent with this project's "fail loudly at the boundary, not internally" philosophy for a hard error, but notably does *not* fail loudly for a silent schema drift; a renamed field would just quietly produce worse data, not an error. Worth a follow-up validation layer if GitHub data quality ever becomes suspect.
5. **Is `FetchedPost` a good fit for GitHub issues, or does it lose information?** Loses issue **state transitions** (labels, assignees, linked PRs, reaction types beyond 👍/❤️, close/reopen history) — `FetchedPost` is deliberately source-agnostic and minimal, so this is expected, not a defect; `raw` carries `{repo, number}` only, for debugging, per the model's own documented "never rely on `raw` from generic code" rule.
6. **What happens at scale (1000 repos, 50 concurrent users)?** Not production-ready at that scale: no rate-limit tracking (60/hr unauthenticated will be exhausted almost immediately across many repos), no caching of issue/comment responses (unlike `CachingAIProvider` for AI calls, there's no equivalent for fetcher HTTP calls), no concurrency control, and — same as `RedditFetcher` today — no async/parallel fetching, so `N` issues means `N+1` sequential HTTP round trips.
7. **Production-ready? PARTIAL.** Solid as a single-user, single-repo-at-a-time, offline-testable fetcher matching the existing `Fetcher` contract exactly, with real, correct, verified error handling for the documented failure modes. Not production-ready for multi-tenant or high-volume use: no rate-limit budget management, no response caching, no retry/backoff, and it isn't wired into the CLI/API yet at all.
8. **Known limitations** (also listed above under Known Issues): comments collapse into the parent issue rather than becoming independent evidence items; no retry logic; not wired into CLI/API; no local rate-limit awareness; no caching of GitHub API responses; silent (not loud) degradation on unexpected schema drift in GitHub's response shape.

### Architecture Review

**Bugs found this session** (both caught and fixed before considering the task done, not shipped):
1. Three of this session's own new tests bypassed output-directory isolation and wrote real files into the project's `output/` directory — a recurrence of Task 8's `Path("unused")` lesson in a new form (this time, forgetting to route through a fixture rather than forgetting to use `tmp_path` directly). Documented here and in the test that discovered it, rather than hidden.

**Technical debt:**
- `report_id` correlation is an O(n) "search every summary file's content for a match" operation, because `Pipeline.run()` has no run-identity concept of its own to return directly — acceptable at personal-tool scale (dozens of files), real debt if this ever needed to scale.
- `GET /reports/{id}` can only return a *structured* report for the run that's still in memory (i.e., the one just returned by `POST /analyze`) — historical lookups get the execution summary (structured) plus raw Markdown text (not re-parsed into JSON), because the pipeline never persists a JSON form of `InsightReport` for past runs. An honest architectural gap, not a bug — but real API consumers should not expect `GET /reports/{id}`'s response to have a populated `top_opportunities`-equivalent field the way a fresh `/analyze` response does, since it doesn't.
- `_OUTPUT_DIR` in `routes.py` and `--output-dir`'s default in `runner.py` are two independent `Path("output")` literals that happen to agree by convention, not by a shared constant — if the CLI's default ever changes, the API's silently diverges.
- No persistence beyond flat files — `GET /reports` is a directory glob, not an index. Fine now; would not scale to a high-volume, multi-user deployment.

**Weaknesses:**
- No pagination cursor for `GET /reports`, only a flat `limit`-capped newest-first list — no way to page past the first N or filter by subreddit/date/success.
- A `None` `report_id` in an otherwise-successful `POST /analyze` response (the correlation-miss case) is only visible by inspecting server logs, not surfaced as a warning in the response body itself — a small tension with this project's "never silently discard failures" principle, worth a follow-up field rather than fixed unasked here.
- No example request bodies attached to the Pydantic models for Swagger UI's "Try it out" — functional OpenAPI docs, but not maximally polished ones.

**Scalability concerns:**
- **A real, newly-introduced concurrency race**: `ResponseCache.set()` (Task 8) does a full read-modify-write of `.cache/ai_responses.json` with no file locking — safe for a human running one CLI command at a time, but the API is the first thing in this project that makes two simultaneous `/analyze` calls plausible, and two concurrent writers to the same cache file can lose an update. Not fixed here (would mean changing `src/pipeline/cache.py`, core pipeline logic, out of scope) — flagged as the most concrete scalability risk this task surfaced.
- `POST /analyze` blocks its worker thread for the full pipeline duration (seconds to minutes for a real run) — FastAPI runs sync handlers in a thread pool, so this works, but a thread pool is finite; there is no background-job/polling pattern, and none was built, since the pipeline itself has no async story to build on and adding one would be a real redesign.
- Flat-file report storage in a single directory doesn't scale past a few thousand files — fine at current, single-user scale.

**Is the API production-ready?**

No, and it was never trying to be — this stays consistent with the project's "personal tool" framing, not a regression. Concretely blocking production readiness: no authentication (anyone reaching the port can trigger real-cost Gemini/Reddit calls and read every past report), no rate limiting, the cache-file concurrency race above, fully synchronous long-running requests with no timeout/job-queue story, and the same-second `report_id` collision. It **is** ready for its actual intended use: a single trusted local user running `uvicorn --reload` and calling it from their own scripts, exactly mirroring what the CLI already offered, just reachable over HTTP instead of a terminal.

### Lessons Learned
- When a user pushes back on a setup requirement (here: not wanting a Reddit API key, then not being able to afford Claude), the better fix is usually to make the dependency optional/pluggable at the architecture level rather than a one-off patch — the Reddit mock-mode pattern turned out to generalize cleanly to swapping the entire AI provider later, because it was built as a real abstraction the first time, not a special case.
- Keeping secret-handling logic in exactly one module (`config.py`) paid off a third time — removing Anthropic and adding Gemini was a contained, mechanical change, not a hunt across the codebase.
- **Actually running the code caught two real bugs that reading it carefully did not** (from Task 2) — the Claude/Fetcher coupling and the Windows console encoding issue were both invisible on inspection and obvious the moment the commands were executed. Don't skip the "run it" step even for code that looks correct.
- When a task has an explicit hard gate ("do not begin Task 3 until X works"), build everything up to that gate, verify what can be verified without the missing piece (mock mode here), and then actually stop and ask — rather than assuming the missing external dependency will show up and reporting premature success.
- Finding an unexpected file (`TODO.md`) mid-task is worth reading fully and reconciling explicitly, not working around silently — it surfaced a real, valid process concern that deserved an on-the-record answer either way.
- **A model "being listed" by an API is not the same as being usable by a given key** — `client.models.list()` returning a model doesn't guarantee `generate_content()` will accept it for that specific key. The only real test of "does this model work" is calling it, not enumerating what's technically listed. Worth remembering before ever hardcoding a specific model name again without testing it against the real key first.
- When a default value (a model name, here) turns out to be wrong, don't just patch the symptom — test the fix against the real dependency before committing to it, the same way the original default should have been tested rather than assumed.
- **Don't trust a clustering/dedup heuristic until it's tested against a case specifically designed to require it.** The mock dataset's duplicate pairs existed since Task 2 for exactly this reason and it was worth actually running the full 7-item set, not just a 3-item sample, before calling the aggregation requirement done — the failure was invisible on smaller runs and in code review, only visible once real output was inspected against known ground truth.
- Quantifying a suspected weakness (computing actual Jaccard scores) turned "clustering seems weak" into "clustering is off by roughly an order of magnitude" — a much more useful finding for a review than an impression, and cheap to produce since it reused already-generated data instead of new API calls.
